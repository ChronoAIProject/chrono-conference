# 第四章 CMA：云端托管 Agent 与事件网关

让一位系统工程师在笔记本上开五个终端、维护本地 Git 工作树并挂起代理隧道，他得心应手；让一位花店店主、财务主管或社群运营照做，五分钟后他就会把电脑合上。

**`CMA`（`ChronoAI Managed Agent`，线上入口 `cma.nyxid.ai`，仓库 `ChronoAIProject/cma`）** 与事件网关 **`cmaeg`** 要干的事再直白不过：把云端托管智能体做成通电即转的工业整机，而不是留给客户照着二十页运维手册拼装的散件。**`v0.12.0`** 已于 **2026 年 11 月 24 日**落盘（`main` 提交 `8f5ba69408`），同日公开仓库补齐 **`Apache-2.0` 开源许可**（PR `#3647`）；而 `develop` 分支在 **14 天内一路碾过 `723` 个合并 PR**，于 **11 月 27 日**推进至 **`3fa2aaf1fb`（PR `#4243`）**，穿越发布列车 Trains `02→17`，把分布式契约 `TC-040`、`TC-045` 与 `TC-070` 逐条焊进了真集群。

## 两大核心服务 + K8s 沙箱控制器撑起的四层云端底座

在真实生产集群里，每多拆出一个独立常驻进程，就多一颗凌晨三点随时误炸的值班传呼机。`CMA` 拒绝拿十几个互相扯皮的微服务装点架构图，直接把整片云端控制面削到骨头——**只留两套应用服务（`cma-agent-manager`、`cma-event-gateway`）加一座 Kubernetes `agent-sandbox` 控制器**；三件可动部件从底向上，干净撑起四道安全边界：

::: {.figure src="ch04-cma-four-layers"}
**`CMA`（`v0.12.0`，`Apache-2.0`，`cma.nyxid.ai`）四层云端托管架构。** 底层由 Kubernetes `agent-sandbox` 控制器与 `chrono-sandbox` 隔离沙箱承接，中上层收敛于 `cma-event-gateway`（`cmaeg`，覆盖 6 大 IM 平台 + `github`/`custom`）与 `cma-agent-manager`（托管运行时、约 `2.1 s` 凭证热重载与操作审计界面）；全程经 `NyxID` 零密钥代理对外通信。
:::

逐层拆解这四层与物理服务的对应关系：

1. **第一层：隔离沙箱执行与产物仓库（K8s `agent-sandbox` 控制器 + `chrono-sandbox`）**：每个托管智能体实例运行在独立隔离沙箱中，支持暂停、唤醒、生命周期管理、独立文件树、文档版本修订与受限只读分享链接，彻底隔绝跨租户文件系统与进程状态。
2. **第二层：多渠道事件网关 `cmaeg`（`cma-event-gateway`）**：把现实世界里形态各异的异步消息——**6 大 IM 平台（`telegram`、`lark`、`feishu`、`discord`、`slack`、`whatsapp`）外加 `github` 与 `custom` 自定义事件**——统一收口到分区事件线程，完成签名核验、重试去重、路由防抖以及发信前的两阶段预备／提交（`prepareoutboundmessage` / `commitoutboundmessage`），避免外部群聊里出现尴尬的重复刷屏或静默丢单。
3. **第三层：托管运行时与约 `2.1 s` 凭证热重载（`cma-agent-manager`）**：**（类比）** 传统云端代理把密钥焊死在容器启动环境变量里，增删一条服务权限就像为了拉一只断路器而炸掉整座变电站——正在跑的长任务当场中断。`CMA` 把凭证平面与沙箱进程解耦：一旦在 `NyxID` 里授权或紧急吊销某项服务，运行中的托管实例无需重启容器，在**约 `2.1 s`**（归档实测文档读数：空闲 `2.152 s` / 忙碌 `1.804 s`）内即可热收敛到新权限集——加权瞬间生效，止血瞬间断电。
4. **第四层：协作与审计工作面（`cma-agent-manager`）**：提供实时事件流、对话转录、沙箱文件树浏览、权限审批队列与用量报表，让业务负责人不必登服务器翻原始日志，就能看清智能体刚动过哪份文档、发过哪条外部消息。

## 十四天七百二十三个 PR：生产事故抢修与分布式护栏

把 `CMA` 推上真集群跑满两周、`723` 个合并 PR 背后藏的不是纸面规划，而是实验台上一桩接一桩真实卡死后拆机焊出来的硬护栏。第一场抢修救回的是 **9 座卡死在镜像轮换途中的线上沙箱**（PR `#3234`、`#3259`、`#3318`、`#4098`）：当时 `image_rotation` 在 `conversation_reopen` 环节撞上 `terminal_validation` 故障，界面既不报错也不退场，只把用户锁在一枚永不停歇的加载转圈后干等。团队没有拿盲目重试掩盖卡死，而是拆掉悬空状态机，引入清晰的**停泊运行时状态（parked-runtime）**与**所有者主动恢复路径**——从此任何轮换异常都必须明明白白停在应急车道并把扳手交回所有者，绝不拿无限转圈糊弄人。

第二场硬仗打在并发切换的毫秒裂缝里：当活跃智能体正往新沙箱切换运行指针、隔壁热备池回收器又在同时清扫空闲备机时，稍一错拍，要么把现网流量切进垂死容器，要么把刚刚认领的备机拦腰砍断。解法是用**单次部署作用域的泳道护栏事务（deployment-scoped lane fence）**把运行时指针切换焊成原子动作（PR `#4100`），并把热备清扫改成**带 UID 与 `resourceVersion` 双条件的前台排空**，且严格只许动未认领备机（PR `#3959`、`#4229`）。这道机械联锁留下铁律：指针切换只有全成或全退，任何已认领沙箱绝不会被回收器从活跃对话脚下抽走。

第三场排雷发生在受监管 Debian Desktop 基准镜像发版前夜：凭据扫描器当头拍下 **`74` 条阻断告警**，整条发布列车当场拉停。拆箱逐字节排查才揪出藏在机器里的幽灵——构建期重新生成的 Python 字节码缓存（来自 `cryptography`、`Redis` 与 `urllib3`）正把带特征串的测试样本一遍遍写回镜像层。先清掉冗余字节码重生（PR `#4148`），再对剩余 **`65` 条上游遗留项**逐一钉死可验证的**包成员级证据**而非粗暴写进通配白名单（PR `#4238`），这才把 `74` 条阻断悉数放清——留下「每条豁免必有包级物证、绝不拍脑袋放行」的发布纪律。

第四场则把多副本链路与流式交接焊死在同一条证据轨上。多副本负载下，跨节点链路追踪一度在半途神秘断节，所有者切换瞬间还会闪现刺眼的 HTTP `503`。沿中间件执行顺序一路倒查，真相令人拍案：`SetRequestIdLayer` 竟套在了中继路由器的**外层**，跨副本转发根本没把关联标识签进线里。把 `x-request-id` 改成**带签名的副本间关联头**（PR `#3266`），并给每一次跨副本转发与浏览器文件预览补齐**带签名的托管移交证明（signed custody proofs）**（PR `#4227`、`#4228`），审计链条再无暗段；与此同时，**持久化 Responses v2**（PR `#2922`、`#4117`、`#4165`）为实时流接上持久化历史回退，彻底抹掉了所有者交接瞬间的 `503` 断档。四桩硬修共同指向同一句工程真话：真正的分布式可靠不是不出故障，而是每一次故障都在机制层面被永远锁死。

## 诚实写明当前边界：今日仍聚焦单一主编码智能体运行时

**（立场）** 既然把 `v0.12.0` 与 `Apache-2.0` 许可亮在台前，就同样要把今天尚未跨越的边界原样写清，绝不拿路线图冒充现役（同步记录于[附录 B](appendix-b-security-and-readiness.md)）：

- 截至 **2026 年 11 月 27 日**，`CMA` `v0.12.0`（`Apache-2.0`）、两大核心应用服务加 K8s `agent-sandbox` 控制器、`cmaeg` 六大 IM 平台加 `github`/`custom` 路由以及约 `2.1 s` 凭证热重载均已上线服役；
- **但截至今日，云端托管实例仍然只开放单一主编码智能体运行时，尚未在云端公开面提供多异构智能体运行时的自由切换。**

如果一位重度构建者需要同时指挥几十个异构编码与研究智能体、直接操作本地多仓库 Git 工作树与真实浏览器，单靠云端单运行时远远不够——于是 ChronoAI 为他们造了整车的另一半驾驶舱：本地优先的多供应方空间编排画布 **`heca`**。第五章推开它的工作台。
