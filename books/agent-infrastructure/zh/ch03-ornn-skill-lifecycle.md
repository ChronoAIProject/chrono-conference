# 第三章 Ornn：面向 Agent 的技能生命周期 API

今天在许多正在试水智能体的团队里，常见一幅石器时代的景象：所谓「技能」就是某条群聊里复制粘贴了七次的 Markdown 碎片——没有版本号、没有安全扫描、没有权限依赖清单；哪天谁顺手改坏了一行，没人知道是谁动的、什么时候上线、又波及了哪几位正在值守的 AI 员工。

**（类比）** 用这种散装碎片跑生产智能体，就像照着贴在未标号阀门上的手写便利贴开化工厂——没有批号、没有纯度化验单、没有化学品安全说明书（MSDS），直到管道冒烟才开始翻聊天记录。软件工程耗费数十年建起包管理器、制品签名与语义化版本规范才逃离那场噩梦；智能体生态却一再忘记同一条铁律：**只要一段工作流指令能够触发真实的 API 写操作、资金流或外部通知，它就不是文学提示词，而是可执行软件——必须按软件的铁律管完整个生命周期。**

**（立场）** 拿一把锤子敲敲市面上花哨的「提示词商店」：好看的卡片封面与五星好评证明不了任何可靠性；真正能交付给机器高频调用的基础设施，靠的是静态安全审计、不可变版本、明确权限清单与成百上千份自动化测试。这就是 **`Ornn`**（线上 `v0.18.0` Alpha，`https://ornn.chrono-ai.fun`）与公开技能目录 **`nyx-skills`** 存在的全部理由。

## 五段式技能生命周期：从 OpenAPI 合成到 AgentSeal 验货

`Ornn` 从第一天起就定位为**面向智能体与工程流水线的技能生命周期 API**。每一项技能从起草到装入智能体，都像工业试剂罐装一样走完五道不可跳过的硬工序：

::: {.figure src="ch03-ornn-skill-lifecycle"}
**`Ornn`（`v0.18.0`）五段式技能生命周期流水线。** 一项技能依次经历编写或从 OpenAPI 自动生成、AgentSeal 安全扫描、不可变版本冻结并由分发标签（dist-tag）指向、绑定受限 `NyxID` 服务作用域，最后供智能体按版本拉取并留存审计轨迹；支撑 `134` 个 OpenAPI 操作端点（`109` 条路径）、`286` 份测试文件与 `nyx-skills@25ef75934d` 中的 `163` 项公开技能。
:::

逐道检查这五关如何把「散装提示词」改造成可审计软件制品：

1. **起草与自动合成（Author / Generate）**：开发者既可手写标准 `SKILL.md` 与附属脚本，也能直接调用 `Ornn` 的生成端点，从任意 OpenAPI 规范或源仓库合成技能骨架，再经统一结构校验器（`validateformat` / `getformatschema`）验形。
2. **AgentSeal 安全审计（Scan & Audit）**：每一版技能在对外可见前都必须过静态与策略扫描（`rescanskillversionagentseal` / `triggerskillaudit`），筛查越权命令、硬编码秘密与可疑外联模式，并把审计结论永久钉在该版本号下。
3. **不可变版本冻结与分发标签（Version & Dist-Tag）**：支持精确语义化版本、跨版本差异对比（`diffskillversions`）、显式弃用标记（`setskillversiondeprecation`）与 dist-tag 切换，彻底杜绝「静默覆写线上正在运行的规程」。
4. **绑定 `NyxID` 服务作用域（Service Binding）**：技能包自身不携带任何明文密钥，只声明它需要哪几项 `NyxID` 代理服务（`setskillnyxidservice`），让管理员在安装前一眼看清最小权限面。
5. **闭合包拉取与使用遥测（Agent Pull & Telemetry）**：借助官方 TypeScript SDK（`v0.4.0`）与 Python SDK（`v0.2.0`），云端 `CMA`、本地 `heca` 与 `NyxBot` 均可按精确版本号拉取传递依赖闭合包（`getskillclosure`），并留下完整调用与拉取遥测。

把这台锻造炉放到日常高密度运维里，更能看出它与「群聊复制粘贴提示词」之间的物理代差。散装提示词最常见的死法不是一开始写错，而是**漂移**——财务或礼宾刚改好一条合规边界，半数代理却还跑着上周二的旧拷贝。`nyx-skills` 用**按小时自动对账的 Ornn 镜像流水线**掐死了这种人工掉队：单在近 14 天内，覆盖财务、人事、礼宾接待与对抗性评审的 **`347` 次提交**持续落盘、自动过审并按小时收敛进 `Ornn` 注册表，留下一条硬不变量——Git 里的权威技能源码与线上供代理拉取的冻结版本每小时机械对齐，不靠任何人肉搬运。

即便注册表每小时常新，如果还得人工钻进每一名专项代理的配置页挨个重钉基础规程，团队照样会滑回「半数员工跑旧版」的泥潭。`NyxID#2432`（跨 **`86` 个文件**）直接把这道钉选漂移按死在平台接缝上：管理员可通过 `/admin/assistant/system-skills` 精选**至多 `8` 项内置公开 Ornn 技能**，并由**修订号护栏（revision fence）**隔离并发变更；此后在 `NyxBot` 与全部专项代理的每一次所有者回合里，系统自动注入这份带版本护栏的基线技能集——既不需要逐代理手工重钉，也不会在热切换中途撕裂正在执行的上下文。

同时把现状边界如实摆在桌面上：`Ornn` 今日仍明确标注为 **`v0.18.0` Alpha**，面向外部第三方技能作者的公开投稿审核流水线仍在持续扩充中，尚未宣称进入完全冻结的 1.0 稳定期。

现在，钥匙锁进了 `NyxID`，规程封箱进了 `Ornn`。下一层最现实的问题立刻扑面而来：**把这些零密钥、带版本号技能的智能体放进真实生产环境 24 小时上岗，云端怎么托管、本地怎么并发？** 第四章与第五章依次拆解整车的双模运行时：`CMA` 与 `heca`。
