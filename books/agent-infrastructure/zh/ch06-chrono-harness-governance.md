# 第六章 chrono-harness 与 sshx：用可执行判官取代一厢情愿的提示词

在软件工程史上，从来没有哪一次重大事故是因为「规范文档里忘写一句『请小心编程』」而发生的。规范失效，几乎永远是因为它只活在散文里，却没有活在编译器和判官程序里。

当智能体以每周数千次提交的速度往仓库里灌入代码时，靠「提示词提醒」维系工程纪律不仅幼稚，而且危险。把一百条原则写进 `AGENTS.md` 却不配自动化判官，就像在高速公路上撤掉全部护栏和测速雷达，只在路边插一块牌子写着「请各位自动驾驶车辆发扬风格、减速慢行」。

**`chrono-harness`**（当前正式发布版 **`v0.1.4`**，发布于 2026 年 11 月 13 日；**27.2 万行 Rust** 源码，横跨 **`chrono-harness` 组织下 25 个模块化仓库**，面向 Linux x86\_64 与 macOS aarch64 各提供 **16 个**预编译二进制工具）加上多视角独立评审协议 **`sshx`**（`v1.0.0-beta.58`，2026 年 11 月 25 日），就是整辆车装在刹车踏板上的硬核判官系统。

## 声明式 `FILEMAP` 与 `DELTA` 增量判定流水线

传统 CI 在面对高速并行开发时，常常陷入两个同样糟糕的极端：要么只做浅层语法检查放过真实回归，要么每改一个标点符号就把全仓耗时两小时的端到端浏览器矩阵全量重跑一遍，把队列彻底堵死。

`chrono-harness` 沿着五步确定性流水线把这对死结切开：

::: {.figure src="ch06-harness-delta-pipeline"}
**`chrono-harness`（`v0.1.4`）声明式 `DELTA` 增量判定流水线。** 从 Git Diff 出发，经显式 `FILEMAP` 依赖登记表（漏登即拒、绝不猜测）计算传递闭包，选出已登记的受影响检查集，以「候选判官执行、基线仅作固定数据」原则输出结构化通过／失败证据回执；同时诚实保留 `SPEC.md` 中的 `completeness_proven: false` 边界声明。
:::

把这条流水线最锋利的四条规则拆开，再用交互实验台 **`HARNESS//DELTA`**（客户端 14 节点示意依赖模型）逐一亲手拨动：

### 规则一：按 `DELTA` 精确选测，拒绝无脑全量重跑

修改了一章纯文字 Markdown 时，到底该跑哪些检查？在下面的 `prose-edit` 示意工况里，点亮单章文字节点后，传递依赖只命中结构校验与双语对齐（示意模型中 `2 / 14` 个单元），省去模型内 `86%` 的无关浏览器与构建开销——展示声明式 `DELTA` 选择如何将本地与 CI 的检查收窄到同一套显式依赖边。

::: {.viz src="harness-delta-judge" preset="prose-edit" height="500"}
**纯文本改动（`prose-edit`）。** 示意修改单个文档节点后，声明式 `DELTA` 选择器仅唤醒受其直接影响的结构检查单元（`2 / 14`），跳过示意图中无关模块，省去模型内约 `86%` 验证成本。
:::

### 规则二：核心变动沿显式依赖边传递展开

反过来，如果改动落在了底层核心引擎或共享运行时节点，`DELTA` 选择器绝不手软——沿 `FILEMAP` 的全部下游依赖边做精确广度优先展开，把包含核心节点在内共 `9 / 14` 个受影响单元一次性纳入必检范围，一个不漏。

::: {.viz src="harness-delta-judge" preset="core-change" height="500"}
**核心引擎改动（`core-change`）。** 改动底层核心节点沿 `FILEMAP` 有向边传递展开，精确点亮包含核心节点在内的 `9 / 14` 个受影响单元进入强制判定队列。
:::

### 规则三：同时修改规则与产品时发出可见警告（`policy.mixed-warning`）

最隐蔽的作弊方式，是在改坏业务代码的同时顺手把判分规则放宽。`chrono-harness` 的 `policy.mixed-warning` 规则并不靠人工官僚审批把改动强行拦死，但只要一次改动同时碰到了产品代码与治理政策节点，品红色混合改动警告立刻高亮，强制扩大验证范围并把两组改动的影响成本分开列账。

::: {.viz src="harness-delta-judge" preset="mixed-policy" height="500"}
**政策与产品同改警告（`mixed-policy`）。** 当变更集同时触及产品节点与判官规则节点，系统强制触发品红色 `policy.mixed-warning` 可见告警并扩展核验边界。
:::

### 规则四：漏登就报错，绝不靠猜（`registry.explicit`）

许多智能构建工具在遇到一个陌生文件时，喜欢靠文件名后缀或正则猜它该跑什么测试——猜漏了就是静默线上事故。`chrono-harness` 执行冷酷的「故障关闭（fail-closed）」原则：**任何未在 `FILEMAP` 显式登记归属与依赖边的新增或变动文件，判官直接报错拒收**，逼着提交者先补齐清晰依赖边，既不靠猜，也不拿盲目全测敷衍。

::: {.viz src="harness-delta-judge" preset="missing-edge" height="500"}
**漏登即报错（`missing-edge`）。** 模拟引入未在 `FILEMAP` 登记依赖边的新文件：`registry.explicit` 规则拒绝猜测或静默放行，立即抛出显式登记缺口错误。
:::

## `sshx`：当单个视角容易盲区时，引入多视角独立评审

光有静态判官还不够，因为机器单测很难发现语义偷换、需求偏差或「虽然绿灯但解决错了问题」的深层陷阱。`sshx`（`ChronoAIProject/consensus-rnd` `v1.0.0-beta.58`，2026-11-25）把**独立只读评审席位**变成标准化工程协议：由彼此隔离的评审视角分别审视同一份架构方案、代码补丁或形式化陈述，将共识点、分歧点与未证前提写成结构化评审回执，强制在合入前把最容易自欺欺人的盲角照亮。

## 诚实写明规范边界：`completeness_proven: false`

哪怕是对自己最引以为傲的治理工具链，我们也绝不越过证据线多说半句：`chrono-harness` 的 `SPEC.md` 至今明确标注着 **`completeness_proven: false`**。原因很简单——`FILEMAP` 登记边全展开只保证「已登记依赖无遗漏」，不自动保证人类或智能体没有遗漏隐式外部副作用。承认这一边界，恰恰是持续把现实事故沉淀为新判官的起点。
