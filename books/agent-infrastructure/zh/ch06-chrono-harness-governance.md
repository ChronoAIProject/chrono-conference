# 第六章 chrono-harness 与 sshx：用可执行判官取代一厢情愿的提示词

软件工程史上，从来没有哪一次生产事故是因为「规范文档里忘写一句『请小心编程』」而爆发的。规则失效，几乎永远是因为它只活在散文里，却没有活在编译器与退出码非零的判官程序里。

当智能体以每周数千次提交的速度往仓库里灌入改动，指望靠「礼貌祈祷提示词」维持纪律不仅天真，而且致命。**（类比）** 往 `AGENTS.md` 里贴进一百条苦口婆心的守则却不配机器判官，就像拆光高速公路的金属护栏与测速雷达，只在路边插一块木牌写着「请各位自动驾驶车辆发扬风格、减速慢行」。把木牌换回真钢板，就是把祈祷词编译成 Rust 可执行判官。

截至 **2026 年 11 月 27 日**，这套机械刹车系统的活跃主场已全面迁入 **`https://github.com/chrono-harness/`**：

- **活跃模块化组织（`https://github.com/chrono-harness/`）**：包含 **`25` 个非归档公开仓库**（全数活跃更新至 `2026-11-27`），其中 **`20` 个独立版本组件仓**（版本区间 **`v0.1.3`–`v0.1.22`**，`runner v0.1.22` 见 PR `#211`，估算合计 **`27.6 万` 行 Rust**），面向 Linux x86\_64 与 macOS aarch64 各分发 **`21` 个预编译二进制**（双平台合计 `42` 份发布资产）；配套 Copier 模板已迭代至 **`v0.1.52`**（`2026-11-27`），规则库扩充至 **`29` 条原子规则**——最新加入的 **`communication.plain-language`**（说人话、禁空洞黑话）与 **`recovery.bounded`**（故障恢复必须有界、禁无限死循环），正是把本手册的工程美学写进机器规则的明证。
- **历史单仓归档说明**：原综合单仓 `ChronoAIProject/chrono-harness`（曾于 `2026-11-13` 发布 `v0.1.4`）已于 **`2026-11-22` 正式归档**，代码规模冻结在 `271,797` 行 Rust；所有新开发与工具拉取一律以 **`https://github.com/chrono-harness/`** 为唯一活跃入口。
- **许可现状坦诚标注**：`chrono-harness` 组织下仓库目前为**源码公开、根级 `LICENSE` 待补齐**（派生默认指令集附 `Apache-2.0` 来源许可）；而配套的多视角独立评审协议 **`sshx`**（`ChronoAIProject/consensus-rnd`，**`v1.0.0-beta.58`**，`2026-11-25`）明确采用 **`MIT`** 开源许可。

## 声明式 `FILEMAP` 与 `DELTA` 增量判定流水线

高速并发仓库最容易跌进两口同样致命的深坑：要么只跑浅层语法检查放任真实回归流进 `main`，要么改一个逗号就把耗时两小时的全仓浏览器矩阵全量重跑一遍，把所有人堵死在队列外。

`chrono-harness` 用一条五步确定性流水线把这对死结劈开：

::: {.figure src="ch06-harness-delta-pipeline"}
**`chrono-harness`（`https://github.com/chrono-harness/`，每平台 `21` 二进制 / `29` 条原子规则）声明式 `DELTA` 增量判定流水线。** 从 Git Diff 出发，经显式 `FILEMAP` 依赖登记表（漏登即拒、绝不猜测）计算传递闭包，选出已登记的受影响检查集，以「候选判官执行、基线仅作固定数据」原则输出结构化通过／失败证据回执；同时在活 crate 与归档 `SPEC.md` 中诚实保留 **`completeness_proven: false`** 边界声明。
:::

把这条流水线最锋利的四道钢齿拆开，再用交互实验台 **`HARNESS//DELTA`**（客户端 14 节点示意依赖模型）逐一拨动验证：

### 规则一：按 `DELTA` 精确选测，拒绝无脑全量重跑

只改了一章纯文字 Markdown 时，到底该跑哪些检查？在下面的 `prose-edit` 示意工况里，点亮单章文字节点后，传递依赖只唤醒结构校验与双语对齐（示意模型中 `2 / 14` 个单元），直接省去模型内 `86%` 的无关浏览器与构建开销——让本地与 CI 共用同一套显式依赖边。

::: {.viz src="harness-delta-judge" preset="prose-edit" height="500"}
**纯文本改动（`prose-edit`）。** 示意修改单个文档节点后，声明式 `DELTA` 选择器仅唤醒受其直接影响的结构检查单元（`2 / 14`），跳过示意图中无关模块，省去模型内约 `86%` 验证成本。
:::

### 规则二：核心变动沿显式依赖边传递展开

反过来，一旦改动落进底层核心引擎或共享运行时节点，`DELTA` 选择器毫不留情——沿 `FILEMAP` 的全部下游有向边做确定性广度优先展开，把包含核心节点在内的 `9 / 14` 个受影响单元一次性推入必检队列，一个不漏。

::: {.viz src="harness-delta-judge" preset="core-change" height="500"}
**核心引擎改动（`core-change`）。** 改动底层核心节点沿 `FILEMAP` 有向边传递展开，精确点亮包含核心节点在内的 `9 / 14` 个受影响单元进入强制判定队列。
:::

### 规则三：同时修改规则与产品时拉响可见警报（`policy.mixed-warning`）

自动化治理里最阴险的作弊，是在改坏产品代码的同时顺手把判官标准放水。`policy.mixed-warning` 不靠官僚签字把改动卡死，但只要同一次变更同时碰到了产品节点与规则／判官节点，显眼的混合改动告警立刻亮起，强制分开列账前后影响与验证成本并扩大核验边界。

::: {.viz src="harness-delta-judge" preset="mixed-policy" height="500"}
**政策与产品同改警告（`mixed-policy`）。** 当变更集同时触及产品节点与判官规则节点，系统强制触发 `policy.mixed-warning` 混合改动可见告警并扩展核验边界。
:::

### 规则四：漏登即报错，绝不靠猜（`registry.explicit`）

许多构建脚本遇到陌生文件时，习惯按后缀名或目录猜它该跑哪套测试——猜漏的那一次就是静默线上事故。`chrono-harness` 执行冷酷的「故障关闭（fail-closed）」铁律：**任何未在 `FILEMAP` 显式登记归属与依赖边的文件变动，判官直接报错拒收**，逼着提交者先补齐清晰登记边，既不靠猜，也不用盲目全测敷衍。

::: {.viz src="harness-delta-judge" preset="missing-edge" height="500"}
**漏登即报错（`missing-edge`）。** 模拟引入未在 `FILEMAP` 登记依赖边的新文件：`registry.explicit` 规则拒绝猜测或静默放行，立即抛出显式登记缺口错误。
:::

## `sshx`：当单一视角天生有盲区，引入独立只读评审席位

机器单测能抓崩掉的不变量，却抓不住语义偷换、需求跑偏或「虽然全绿但解决错了问题」的深层幻觉。**`sshx`**（`ChronoAIProject/consensus-rnd` **`v1.0.0-beta.58`**，`2026-11-25`，**MIT** 许可）把**彼此隔离的独立只读评审席位**写进标准化工程协议：不同视角分别审视同一份架构方案、补丁或形式化陈述，将共识点、分歧点与未证前提写成结构化评审回执，在合入之前把最容易自欺欺人的盲角照亮。但正如第三卷第七章的人机协同消融图（`ch07-hitl-ablation-gate`）实证所示，单靠只读散文评审席位仍会残留 `20%` 的相关假阳性「审稿注水」，唯有将其与可执行反例义务闸门硬耦合，才能把假阳性率从 `30.0%` 一举压至 `0.0%`。

## 值得骄傲的硬编码诚实：`completeness_proven: false`

把规矩编进判官之后，紧接着要防的是**判官自己生锈或失灵**。翻开 `chrono-harness` 组织下 `16+` 个仓库的源码，两条彼此咬合的形式化防线直接锁死在刹车卡钳与规则模型上：

- **`540` 份 `verus!` 形式化验证 Rust 源文件（跨组织 `856` 处引用）**：专给每一只刹车卡钳上数学铁锁——`verified_bytes.rs`（PR `#84`）证明规则输出与规范字节逐字节一致，杜绝编译产物悄然漂移；PR `#119` 证明一旦 `git fetch` 遭遇 OID 不匹配，临时引用必被清理干净，绝不在仓库里遗留悬空脏引用；PR `#73` 则拿 **4 种刻意注入的故障变异**反打 `judge-mixed` 调度器，证明混合政策告警不可能在产品与规则同改时被静默捂嘴。
- **Z3 `4.12.5` 形式化反例模型校验 `recovery.bounded`（`chrono-harness-instructions#90`）**：连面向智能体行为的故障恢复规则也配上了可执行数学模型，四项求解结果（**`unsat, unsat, sat, sat`**）亲手构造出一条可达反例——**如果智能体在重试前不先核验前一次操作是否已对外生效，盲目重试必然触发双重写入（double-write）事故。**

**（立场）** 正因为把每一只刹车卡钳都推到了 Verus 与 Z3 形式化证明的精度，我们才更有底气把最刺眼的一行布尔值摆在正中央：**`completeness_proven: false`** 至今直接**硬编码在 `chrono-harness` 的现役 Rust crate（`runner`、`inputs`、`judge-*`、`cache`）以及已归档的 `SPEC.md`（`parity: unestablished`）里**。

一块在超出量程时诚实打印 `UNKNOWN` 的仪表，是科学仪器；一块无论发生什么都把灯刷绿的看板，是宣传海报。给每一只刹车卡钳做完形式化证明，却绝不妄称全知全能——`FILEMAP` 传递展开只保证「凡是已登记的依赖边一条不漏」，绝不自夸能穷尽人类尚未登记的隐式外部副作用。守住这行 `completeness_proven: false`，正是不断把真实故障锻造成下一枚可执行判官的起点。
