# 第一章 NyxID：零密钥连接与身份底座

把公司的生产 API 密钥写进 `.env` 文件，再塞给一个能浏览公开网页、能拆陌生人邮件、能执行外部工具的自主智能体——**（类比）** 这等于把酒店总保险柜的密码抄在信封背面，交到泊车员手里，再派他穿过一条满是扒手的街。

只要一页带毒的外部网页里藏着两行间接提示注入，智能体就会把环境变量里每一把密钥打包寄给攻击者。更荒诞的偶像崇拜，是某些团队在系统提示词末尾加上一句大写加粗的「**严禁泄露任何密钥！**」便以为高枕无忧。**（立场）** 拿一把音叉敲敲这种「提示词安全观」，发出的全是空响：靠祈祷文字管住权限不是安全工程，只是巫术。理查德·费曼在 1986 年《挑战者号事故总统委员会报告》附录 F 里留下的冷酷定律同样刻在安全边界上：现实不会被公关欺骗，攻击者更不会因为你在提示词里用了三个感叹号就收手。

**`NyxID`** 从一条不讲情面的机械前提起步：**不要指望智能体「自觉保守秘密」——从物理与网络拓扑上，让它压根摸不到任何明文秘密。**

## 酒店房卡，而不是总保险柜密码：四道硬隔离边界

**（类比）** 真正成熟的酒店从不把总保险柜密码交给前台临时工或泊车员，只发一张磁条房卡：它只能打开 412 号房门、中午十二点自动失效，一旦前台在后台一键挂失，卡片立刻变成一块毫无价值的塑料片——泊车员从头到尾连主保险柜长什么样都没见过。

把 `NyxID` 的代理架构垂直剖开，正是这套机械隔离的四层实体实现：上方的智能体运行时手里只有一张窄作用域、短寿命、不透明的能力句柄（那张只开 412 室的房卡）；所有真正的 OAuth 令牌、上游 API 密钥与刷新凭据全部封存在加密代理金库内存里，在请求跨过边界发往上游服务的最后一毫秒注入，并在响应返回模型上下文之前把所有敏感响应头洗得一干二净。

::: {.figure src="ch01-nyxid-proxy-layers"}
**`NyxID` 四层零密钥代理安全边界。** 智能体上下文始终保持零明文秘密，仅持受限能力句柄；所有调用必经策略关口，高危写操作另需人工审批，再由加密金库在代理内存完成 OAuth/API 令牌注入与响应清洗，线上 `v0.78.0` 统一对接 55 项内置服务、42 份 OpenAPI→MCP 规范、7 家 LLM 网关、9 类消息渠道（10 适配器）与 5 套通话／语音配置。
:::

不用听空口承诺，直接上撞击台。在下面的交互实验台 `NYXID//VAULT` 里，把「传统明文直连」与「`NyxID` 零密钥代理」丢进同一场提示注入攻击。先看 `direct-leak` 工况——当 $k$ 项外部服务的明文密钥直接躺在传统智能体的上下文或环境变量里，一次带毒外部响应就能横向卷走全部钥匙，爆炸半径随挂载服务数 $k$ 线性飙升：

::: {.viz src="nyxid-credential-flow" preset="direct-leak" height="500"}
**传统明文注入泄露（`direct-leak`）。** 对比传统 `.env` 直连模式下，一条恶意外部响应如何在单轮内横向窃取全部挂载服务的明文凭据，暴露密钥数随连接服务数 $k$ 线性放大。
:::

现在把完全相同的带毒载荷切进 `scoped-proxy` 工况：`NyxID` 策略引擎当场核验能力句柄的最小作用域（例如仅限 `read:issues`），拦死越权横向调用；更重要的是，模型上下文里压根不存在任何明文凭据可供外泄——**暴露密钥数被物理按死在精确的 `0`**。

::: {.viz src="nyxid-credential-flow" preset="scoped-proxy" height="500"}
**受限能力代理（`scoped-proxy`）。** 数据包经 `NyxID` 策略引擎按最小作用域校验，明文令牌只在加密代理内存内注入并剥离，上下文暴露密钥数严格为 `0`。
:::

## 不停机退役主密钥：线上密钥环普查与密码学防篡改

把 49 张生产集合里的加密凭据全部扛在肩上，迟早要撞上密码工程里最棘手的一道考题：怎样在不停服、不断线的前提下淘汰旧主密钥，并且保证数据库里哪怕被写入恶意密文也没法蒙混过关？**（类比）** 这好比在一家 49 层满房运转的酒店里，趁所有房客熟睡，逐扇拆换每一间客房的锁芯——不仅不能停电清场，还得堵死一个极隐蔽的暗门：决不许有人把 1408 室的合法密文原样挪到 3201 室的门板上骗过解密校验。在 `dev 0.79.0` 近 14 天落地的 **`170` 个合并 PR** 里（截至 `6784b6dd36`），实验台先拿「逐记录密码学绑定」焊死了移花接木（PR `#2892`–`#3002`）：每条密文字段必须携带按集合、记录与字段类型生成的强类型 `crypto::record_field` 附加认证数据（AAD），同时用 Rust `Zeroizing` 内存缓冲区在释放瞬间覆零明文密钥材料，跨记录掉包密文连第一道验签都过不了。紧接着，`ring-v1` 线上密钥环普查把停机维护窗彻底送进了历史（PR `#3011`、`#3081`、`#3091`）——系统仅在启动时读取一次 `encryption_key_lifecycle._id = "ring-v1"` 闸门标记，随后用只读快照叠加 MongoDB 变更流观察者在线扫完横跨 **`49` 张集合的全部 `51` 条注册表条目**，让旧主密钥在零维护窗口下平稳退役。留下的是一条冷硬不变量：旧密钥在线清零不停服，任何脱离原记录身份的密文碎片当场失效。

密钥在库里锁稳之后，实验台紧接着在传输线与并发队列里揪出三道同样尖锐的裂缝。第一道出在 Webhook 验签上：过去签名覆盖时间戳与报文体，却漏掉了投递编号，中间人一旦篡改 `X-NyxID-Delivery-Id` 便可能伪造或重放投递身份。新的 `X-NyxID-Signature-V2`（PR `#3089`）把无歧义的空字节分隔帧 `version || NUL || timestamp || NUL || X-NyxID-Delivery-Id || NUL || raw_body` 整段签进摘要，彻底封死投递编号欺骗。第二道出在异步后台队列的权限时间差里：当组织刚刚把某名成员降权、移出或抹除时，几秒前已入队的后台任务依然可能醒来并按旧身份继续执行。跨 `100` 个文件落地的单调递增计数器 `OrgMembership.eligibility_revision`（PR `#3085`）给出了手术刀般的解法——该版本号在降权、移除或抹除时原子自增、在提权时刻意绝不递增，每条排队作业核验失败即在半空中被直接截杀；同时数据库层启用 MongoDB 8 `prepareUnique` 在线收紧所有者隔离唯一索引（PR `#3090`），不锁表完成约束切换。这三条补丁钉下了三道线级不变量：投递编号不可伪造，被撤销的权限绝不在队列里借尸还魂，租户所有者隔离在线生效不阻塞现网流量。

## 透明计量：`1 credit = 1 USD` 与 BYOK 硬熔断

把 AI 员工接进真实业务时，紧跟密钥泄露身后的第二场惨剧就是**失控账单**——一只卡在重试死循环里的智能体，完全可以在一个周末把一张没有上限的企业信用卡刷穿。

`NyxID` 把预算表和门禁锁焊在同一条代理总线上：基于 Lago 与 Stripe 的 Credits 计量采用毫无花哨换算的硬口径（**`1 credit = 1 USD`**），同时原生支持企业自带密钥（BYOK）透传，并在每个智能体实例上执行不可绕过的消费封顶。下面这张 `billing-meter` 实验卡演示单次调用如何同步走过作用域校验、计量落账与触顶硬切断：
